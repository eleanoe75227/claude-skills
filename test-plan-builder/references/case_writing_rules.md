# 測試案例寫作規則：前後對照範例

來源：某行政系統建置案，測試計畫初稿交SA審閱後的實際回饋（SA以反黃標示問題文字、另色文字說明、Word註解提問）。以下每條都是「初稿寫法 → SA回饋 → 修正後寫法」，寫新案例時可直接比照。

---

## 規則1：每條步驟、每條預期結果都要對得回規格原文

**典型錯誤：自行延伸規格沒寫的情境。** 每一條單獨看都合理，但規格沒要求、系統不一定有做，SA會整批標黃。

| 規格原文 | 初稿多寫的（被標黃） | 修正後 |
|---|---|---|
| 申請者可輸入備註，並顯示於申請單、報表、簽收表 | 「輸入超過字數上限之內容」「超過字數上限被阻擋」「未填備註時報表列高不增加」 | 只驗證備註有顯示在三個地方 |
| 庫存於申請成立時同步扣除 | 「A撤回或退回申請單後，庫存數恢復」 | 只驗證B看到的庫存已扣除A的申請數量 |
| 物品退回僅限當月辦理，跨月不得退回 | 「管理員與申請者皆不可」「並有明確提示或按鈕不可用」 | 本月可退回、上月不可退回 |
| 駕駛僅可檢視指派予本人的派車單 | 「嘗試以搜尋或網址查看其他駕駛的派車單」 | 列表僅顯示指派予本人的派車單 |
| 簽核完成後通知具指派權限之管理者 | 「不具權限者未收到」「信件帶有效數位簽章」 | 具權限者收到通知信 |
| 設定建議申請數量／限制申請數量 | 「白名單單位不受限制」「申請數量超過庫存量時提交」 | 只驗證建議（提示）與限制（阻擋） |

**自我檢查**：寫完一條案例，逐句問「這句對應規格原文哪幾個字？」答不出來就刪。

## 規則2：不寫開關／組態／後台設定步驟

SA原話：「所有測試步驟都不需要寫去做什麼開關，這些驗測者不需要知道，除非這個開關是本身的需求。」

| 初稿 | 修正後 |
|---|---|
| 1. 開啟物品管理檢視欄位　2. 依模組／倉庫設定開啟隱藏設定後重新開啟畫面　3. 關閉隱藏設定，確認欄位恢復顯示 | 1. 到「物品管理」功能點選「新增物品」檢視欄位　2. 點選任一物品「編輯」檢視欄位 → 預期：兩個畫面皆不顯示該欄位 |
| 1. 於「分區組態」開啟「指派車輛通知」　2. 完成指派　3. 檢視信件 | 1. 到「指派車輛/駕駛」功能完成指派　2. 至申請者信箱檢視通知信 |
| 預期結果：物品代碼依開關設定產生 | 預期結果：物品代碼自動帶入第一層類別代碼 |
| 補充說明：以「倉庫組態」開關控制，測試時分別驗證開關開啟與關閉 | （刪除） |

## 規則3：驗測者要做得到；做不到的改佐證

| 狀況 | 初稿 | 修正後 |
|---|---|---|
| 驗測者進不了長官信箱 | 「於長官信箱開啟簽核通知信」（SA註解：做不到吧） | 「陳核至簽核者（以另一測試帳號擔任）」「至簽核者測試帳號之信箱開啟通知信」 |
| 交易原子性（使用者操作無法觸發寫入失敗） | 「於測試資料庫模擬寫入失敗，執行入庫，檢視回復」 | 驗證方式：「本項以佐證資料驗證，不列使用者操作步驟。佐證資料：入庫作業之交易控制程式碼片段與說明」 |
| 報表帶值、資料修正方案等只需證明結果 | 列4步操作步驟 | 驗證方式：畫面截圖佐證 |

SA原話：「這裡是要附程式碼／截圖當作佐證資料，沒有要給使用者測試。」

## 規則4：正反向合一案；互斥設定分開對象

| 初稿 | SA回饋 | 修正後 |
|---|---|---|
| 簽核-06 有代理權限者、簽核-07 無代理權限者（兩案） | 和06合併就好，不用分開寫；這裡是純檢視畫面沒有新增功能 | 一案：步驟1 有權限帳號檢視按鈕、步驟2 無權限帳號檢視按鈕；不寫「完成一次代理設定」 |
| 權限-01 匯出、權限-02 匯出範圍涵蓋所有模組、權限-03 無權限者不可匯出（三案） | 不需要分成3個測項 | 一案：匯出並開啟檔案，預期結果列出應涵蓋的模組 |
| 同一物品同時設定建議數量＝5、限制數量＝10 | 這是2選1，所以需要分兩個物品去設定 | 物品A設建議數量、物品B設限制數量，分別申請 |

## 規則5：用客戶環境實際看得到的名稱

| 初稿 | 修正後 |
|---|---|
| 下載「處理中報表」（報表名稱可由語系設定為「未領用報表」） | 點選「未領用報表」下載（SA：直接用客戶環境的報表名稱） |

## 規則6：補充說明欄只寫驗測者需要知道的事

以下初稿的補充說明全部被標黃刪除：

- 「此項會議紀錄記載已於現行版本釋出，本案例作為驗證。」
- 「第一次訪談決議此項待與各業務單位溝通後再處理，第二次訪談紀錄載明暫定作法（備註約10～20字）。」
- 「會議紀錄記載現場實測非系統強制裁切，另約時間請業務單位示範確認問題點。」
- 「通知信目前未顯示送件時間；信件是否增列時間欄位待與SA確認。」
- 「加油量未填時之顯示值（空白或0）依設定，執行時記錄。」

保留的例子：「業務單位曾誤解此功能：清單為空係因未曾代理他人，並非缺少權限；驗證時區分『無權限』與『無代理紀錄』。」——這是驗測者判定結果時真的用得到的資訊。

## 規則7：文件正文不放內部資訊

| 初稿 | SA回饋 | 修正後 |
|---|---|---|
| 測試人員表列出每個角色的人名 | 有需要寫人名？ | 只寫角色與工作內容 |
| 系統總表有「性質（再造／增修）」「開發環境」「案例編號前綴」欄 | 有需要寫嗎？這欄的作用是？ | 只留No.／子系統／需求編號／所在附件 |
| 正文註記「開發環境為.NET，SA文件目前僅載明PHP，待SA補充」 | 標黃 | 刪除；待確認事項用藍字或PM螢光標記處理 |
| 「（機關用語為『系統』，實務上為平台下的功能模組）」 | 標黃 | 刪除 |

## 規則8（預設寫法）：「到『功能路徑』功能，點選『按鈕』」

SA原話：「一般測試步驟我會寫『到OOO功能，點選XXX』，這樣驗測者才會依照你的想法去走。」

| 初稿 | SA回饋 | 修正後 |
|---|---|---|
| 3. 下載「未領用物品報表」，檢視備註 | 漏了「到OOO功能」，什麼地方下載？少了這個客戶會迷路 | 3. 到「領用退回作業」功能，狀態選「處理中」，點選「未領用報表」下載 |
| 1. 新增課程，不勾選「是否分配員額」 | （同規則） | 1. 到「課程＞新增」功能，不勾選「是否分配員額」 |

準備性步驟（「準備本月與上月已領用之申請單各一筆」）、以測試帳號登入的步驟可以不寫功能位置。

## 需求表的整理（配合規則1）

| 初稿 | SA回饋 | 修正後 |
|---|---|---|
| 需求表列入會議memo列 | 所有MEMO都砍掉 | 刪除 |
| 需求表列入「非RFP範疇（後續精進建議）」列，案例欄填「—」 | 不編號是否要說明原因？ | 不在RFP範圍、專案不會做 → 整列刪除 |
| 會議紀錄衍生列與RFP列指向同一案例 | 編號重複？ | 會議紀錄只是RFP條文的補充說明時，只留RFP列 |
| 「未定案」會議項目寫成案例 | 這項能不列嗎？ | 刪除 |
| RFP寫在「簽核」章節的數位簽章需求放在簽核案例 | 這個歸在大量郵件 | 依SA分工表歸到實際負責的模組 |
