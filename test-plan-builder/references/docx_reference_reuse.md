# 延用既有Word文件格式的技巧

適用情境：使用者提供了一份歷史文件（舊版測試計畫、客戶既有範本），要求新文件沿用同一套排版、標題編號、頁首頁尾樣式。這裡整理的是實際專案中踩過坑之後歸納出來的做法，不限測試計畫，任何要延用舊版格式的正式文件都適用。

## 1. 不要用文件處理套件（如python-docx）直接另存來改內容

python-docx讀取一份既有文件、改幾個地方、存檔，看起來最直覺，但存檔動作會把頁首頁尾的參照關係、版面設定、部分樣式重新實體化——原本文件裡沒被程式碰過的部分也可能跑版（例如頁碼欄位、章節分隔設定）。

**做法**：只改文字內容時，直接編輯壓縮檔（.docx本質是zip）內的 `word/document.xml`（需要的話還有 `word/header*.xml`、`word/footer*.xml`），其餘部件（樣式、媒體、關聯檔）原封不動複製。這樣能確保沒被動到的地方維持原樣，不會因為套件重新序列化而跑版。

如果是要「大量產生結構相似的新內容」（例如測試案例一條一條生成，不是改既有文字），可以反過來：寫一支組裝腳本，把母版文件的樣式定義（`word/styles.xml`、`word/numbering.xml`）當基礎，用程式產生新的段落／表格XML片段插入，而不是每次都重新設計樣式。這樣產出的文件會自然套用母版既有的字型、編號、表格框線設定。

## 2. 目錄頁碼要跑多輪，不要一次生成就假設是對的

Word文件如果有自動目錄，頁碼是「內容排版完之後才穩定」的東西——你在寫程式產生內容的當下，不可能準確算出最終會落在第幾頁（字數、分頁、圖表位置都會影響）。常見錯誤是生成時就填一個猜測的頁碼，或乾脆留給Word的「更新欄位」功能，但那需要開啟Word手動觸發，不適合自動化流程。

**做法（三輪修正迴圈）**：
1. 先用暫時／錯誤的頁碼產出文件
2. 轉成PDF（例如用LibreOffice headless：`soffice --headless --convert-to pdf`）
3. 用PDF解析工具（例如PyMuPDF）逐頁掃描，比對每個標題文字實際落在第幾頁，建立「標題→實際頁碼」對照表
4. 拿這份對照表重新產出文件的目錄頁
5. 重複2-4，直到目錄頁碼跟PDF渲染結果完全一致（可以寫個檢查腳本，掃描目錄頁每一行「標題......頁碼」的格式，抓有沒有缺頁碼或格式異常的行數，等於0才算過）

這個迴圈通常跑2-3輪就會穩定（因為目錄頁本身的頁數變化，只在前幾輪會影響後面內容的頁碼位移）。

## 3. 不確定內容的標記慣例

正文裡摻雜「已確認的內容」跟「AI暫定、還沒人確認的內容」，肉眼很難分辨，容易被誤當定案內容處理掉。

**做法**：訂一個簡單、一致的標記語法（例如用某種括號包起來的片段），在組裝文件時偵測到這個標記就把該段文字轉成視覺上明顯不同的樣式（常見做法是轉成特定顏色的字，例如藍字）。這樣不確定的內容在文件裡會自然凸顯出來，不需要每次手動檢查。重點是「格式自動觸發」，不要仰賴人工記得每次都要手動變色——手動的東西久了一定會漏。

## 小結

這三個技巧解決的是同一類問題：**產出流程裡有些東西無法在第一次生成時就確定（頁碼、格式是否延續母版、內容是否已被確認），與其假裝第一次就能做對，不如把「怎麼發現做錯了、怎麼修正」也寫進流程裡。**
