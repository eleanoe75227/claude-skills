# SA審閱回饋：抽取、核對清單與自動核對

適用情境：測試計畫（或任何正式文件）交給SA／審閱者後，對方在Word裡用反黃、另色文字、註解、追蹤修訂標示意見，要逐條修正，並能證明「每一條都處理到了」。

## 為什麼要用程式抽、用程式核

- 審閱者的標記散落在幾十頁、上百個表格裡，人工翻找容易漏；尤其反黃常常只標半句話。
- 「我改好了」不能靠印象。實際案例：一份92段反黃＋20則註解＋十幾處說明文字的回饋，用程式核對時才發現一處自己新寫的提醒文字誤用了已被刪除的字眼，還抓到一個舊版遺留的案例對應錯誤。

## 流程

### 1. 抽取標記，做成核對清單

```
python3 scripts/review_marks.py extract <審閱回饋.docx> > 核對清單.md
```

輸出每筆標記的種類（反黃／色字／註解／修訂）、所在章節、內容與所在表格列的上下文。先跟使用者確認顏色意義（例如：反黃＝文字有問題、藍字＝審閱者說明）。

注意：審閱者說的「反藍」通常是**藍色螢光（反cyan）**，不是藍色字；原稿自己用來標「待確認」的藍字也會以「色字」被抽出來（實測一份回饋抽出96筆色字，幾乎都是原稿自己的待確認藍字）。審閱者的意見以「反色」與「註解」為主，「色字」要先區分是誰寫的。

注意：先檢查有沒有追蹤修訂；審閱者說「看追蹤修訂」但實際只用了反黃與註解的情況很常見，要照實告訴使用者。

### 2. 逐條決定處理方式

在清單的「處理方式」欄填寫：刪除／改寫成什麼／保留（理由）／**無法判斷→列給使用者**。

- 能從規格、SA文件、知識庫查到答案的，直接改。
- 需要使用者或SA拍板的（範圍、實際選單名稱、審閱者語意不明的反黃），不要猜，列給使用者；需要在文件裡留提醒的，用黃色螢光「【PM待確認】」標示。
- 審閱者提出的「寫法原則」（例如PS：所有步驟都不要寫開關），不只改被標到的那幾處，要套用到全文件、所有系統。
- 能通用到其他專案的原則，回寫到 `SKILL.md` 的寫作規則與 `case_writing_rules.md`。

### 3. 修正後自動核對

**反黃文字殘留檢查**（全自動）：

```
python3 scripts/review_marks.py residual <審閱回饋.docx> <新版主文件.docx> <新版附件.docx> ...
```

仍殘留的片段逐一判斷：是漏改，還是合理保留（例如出現在需求表的RFP原文、其他系統本來就有的用語）。合理保留的要能說出理由。

**註解、說明文字、寫法原則**（半自動）：每一條寫成一個可以用程式檢查的條件，例如：

| 回饋 | 檢查條件 |
|---|---|
| 所有MEMO都砍掉 | 全部文件文字不含「memo」 |
| 有需要寫人名？ | 主文件不含任何專案成員姓名（列出名單比對） |
| 主文件都寫完了還要附件嗎？（詳細步驟放附件） | 主文件不含「測試步驟：」；每份附件都含 |
| 做不到吧（進長官信箱） | 全部文件不含「長官信箱」 |
| 壓測有在分模組？ | 壓力測試章不含「單模組」「第一層」「三層」 |
| 整合測試是本年度範圍？ | 整合測試章不含增修系統名稱 |
| 這裡要附截圖當佐證 | 該幾個案例的步驟以「本項以佐證資料驗證」開頭 |
| 所有步驟不要寫開關 | 指定系統的所有案例步驟／預期結果不含「組態」「開關」「依設定」 |
| 步驟寫「到OOO功能」 | 每個案例第一步含「到「」，或為準備／佐證／登入步驟 |

條件寫在一支專案自己的核對程式裡（範例：前一專案的 `verify_sa_feedback.py`，放在該專案 outputs 的工具資料夾），跑到全部通過才回報完成。

### 4. 回報使用者

回報內容要包含：

- 核對了什麼（幾段反黃、幾則註解、幾條原則）與結果（幾項通過）。
- 仍殘留但合理保留的項目與理由。
- 無法判斷、需要使用者或SA決定的清單，**並註明各自在哪個文件、哪個位置、文件上有沒有標記**。
- 審閱範圍以外、順帶套用同原則修改的地方（例如其他SA負責的系統）。

## 同步原則

若文件由程式產出：修正要改在程式的內容資料裡，再重產文件，不要只改Word；使用者在Word裡手改過的內容，重產前先同步回程式（見 `SKILL.md`「Word與建置程式同步」）。
